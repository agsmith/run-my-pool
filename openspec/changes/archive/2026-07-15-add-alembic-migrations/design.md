# Design: add-alembic-migrations

Introduce Alembic as the versioned schema migration system for the RunMyPool backend, replacing the current ad-hoc SQL file approach.

## Context

The backend currently manages schema through `datamodel.sql` (full DDL + seed data) and a collection of ad-hoc SQL files and one-off Python scripts applied manually:

- `alter_schedule_winning_team_id.sql` — changed `schedule.winning_team_id` from `VARCHAR(100)` to `INT NULL`
- `update_enum.sql` — normalized `users.role` ENUM to uppercase values
- `fix_duplicate_constraints.py` — repaired duplicate FK constraint names on the `schedule` table

All three have been applied to production. `datamodel.sql` is partially stale — it still shows `winning_team_id VARCHAR(100) NOT NULL`, while the live schema and `models.py` correctly reflect `INT NULL`. **`models.py` is the authoritative source of truth** for the current schema state.

`main.py` explicitly skips SQLAlchemy's `create_all()` with the comment: "schema is managed by datamodel.sql". That comment needs updating.

Alembic is the standard SQLAlchemy migration tool. It reads `models.py` directly, can autogenerate migration scripts from model diffs, tracks applied revisions in an `alembic_version` table, and supports rollback.

No `docs/dev/architecture.md` exists in the project.

## References

- [Alembic documentation](https://alembic.sqlalchemy.org/en/latest/) — Official docs covering autogenerate, `stamp`, `upgrade`, `downgrade`, and environment configuration.
- [Alembic autogenerate](https://alembic.sqlalchemy.org/en/latest/autogenerate.html) — How Alembic compares models to the live schema to generate revision scripts.
- [Alembic cookbook: don't auto-apply seed data](https://alembic.sqlalchemy.org/en/latest/cookbook.html) — Covers patterns for separating DDL from reference data.

## Goals / Non-Goals

**Goals:**

- Add Alembic to the backend with a single baseline revision (`001`) generated from `models.py`
- Include static reference data (NFL teams, survivor pool rules) in the baseline revision
- Extract season schedule data into a separate `seed_schedule.py` script
- Provide a `alembic stamp head` path for baselining the existing production RDS instance
- Document developer and deployment workflows
- Add `alembic` to `requirements.txt`

**Non-Goals:**

- Replacing or deleting `datamodel.sql` — it remains as a historical reference
- Auto-running migrations during app startup (`main.py` does not call `alembic upgrade`)
- Managing Lambda or CloudFormation schemas
- Schema changes beyond the current state (future schema changes are separate changes)

## Decisions

### D1: Use `models.py` as the autogenerate source for the baseline revision

**Decision:** The baseline revision is generated by pointing Alembic at the current `models.py` via `--autogenerate`, not transcribed from `datamodel.sql`. `datamodel.sql` has a known stale column definition (`winning_team_id VARCHAR(100)` vs actual `INT NULL`). `models.py` reflects the correct prod state.

```python
# alembic/env.py
import sys
import os
sys.path.insert(0, os.path.join(os.path.dirname(__file__), '..'))

from logging.config import fileConfig
from sqlalchemy import engine_from_config, pool
from alembic import context
from models import Base  # all SQLAlchemy models

config = context.config
if config.config_file_name is not None:
    fileConfig(config.config_file_name)

target_metadata = Base.metadata

def run_migrations_offline() -> None:
    url = config.get_main_option("sqlalchemy.url")
    context.configure(
        url=url,
        target_metadata=target_metadata,
        literal_binds=True,
        dialect_opts={"paramstyle": "named"},
    )
    with context.begin_transaction():
        context.run_migrations()

def run_migrations_online() -> None:
    connectable = engine_from_config(
        config.get_section(config.config_ini_section, {}),
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )
    with connectable.connect() as connection:
        context.configure(connection=connection, target_metadata=target_metadata)
        with context.begin_transaction():
            context.run_migrations()

if context.is_offline_mode():
    run_migrations_offline()
else:
    run_migrations_online()
```

**Alternative considered:** Transcribe DDL manually from `datamodel.sql`. Rejected — `datamodel.sql` has at least one known stale definition and using autogenerate ensures the baseline matches actual model state.

### D2: Static reference data (teams + rules) included in the baseline revision; schedule data in a separate seed script

**Decision:** NFL teams (32 teams + `NT`/`LT` sentinels) and survivor pool rules are inserted in the baseline migration revision. The 2025 season schedule is extracted into `seed_schedule.py` and run separately.

Rationale: Teams and rules are permanent, stable reference data — they change only if the NFL expands or the pool rule system is redesigned. Including them in the migration guarantees a fresh environment is fully functional after a single `alembic upgrade head`. Schedule data changes every season; embedding it in a migration would require a new migration revision each year or awkward conditional logic.

```python
# alembic/versions/001_initial_schema.py (excerpt — data section)
from alembic import op
import sqlalchemy as sa

def upgrade() -> None:
    # ... DDL operations (autogenerated) ...

    # Static reference data
    op.execute("""
        INSERT INTO teams (id, name, abbrv, logo) VALUES
        (1, 'Atlanta Falcons', 'ATL', '/nfl/atl.svg'),
        (2, 'Buffalo Bills', 'BUF', '/nfl/buf.svg'),
        -- ... all 32 teams + NT/LT ...
        (98, 'Losing Team', 'LT', '/nfl/red_x.svg'),
        (99, 'No Team', 'NT', '/nfl/green_plus.svg')
        ON DUPLICATE KEY UPDATE name=VALUES(name)
    """)

    op.execute("""
        INSERT INTO rules (id, pool_type, rule_text, rule_type, default_value, enabled_by_default) VALUES
        ('weekly-lock-day', 'survivor', 'Weekly Lock Day', 'selection', '0', true),
        ('weekly-lock-time', 'survivor', 'Weekly Lock Time', 'time', '13:00:00', true),
        ('auto-pick-enabled', 'survivor', 'Auto-Pick Enabled', 'boolean', 'false', true),
        ('auto-pick-strategy', 'survivor', 'Auto-Pick Strategy', 'selection', 'random', true),
        ('game-mode', 'survivor', 'Game Mode', 'selection', 'pick_winner', true),
        ('message-board-enabled', 'survivor', 'Message Board Enabled', 'boolean', 'true', true)
        ON DUPLICATE KEY UPDATE rule_text=VALUES(rule_text)
    """)

def downgrade() -> None:
    # ... drop tables in reverse dependency order ...
    pass
```

**Alternative considered:** Put all seed data (including schedule) in the migration. Rejected — schedule must be replaced annually. A migration file is an append-only history; overwriting it for a new season is incorrect use of migrations.

### D3: Use `alembic stamp head` to baseline production without re-running DDL

**Decision:** The existing production RDS instance already has all tables. Running `alembic upgrade head` on it would attempt to re-create tables and fail. Instead, after Alembic is deployed, production is baselined with `alembic stamp head`, which writes the current head revision ID to the `alembic_version` table without executing any SQL. Subsequent revisions run normally.

```bash
# One-time production baselining procedure (run once after first deploy)
alembic stamp head

# Verify
alembic current
# Expected output: <revision_id> (head)
```

**Alternative considered:** Use `--if-not-exists` guards on all CREATE TABLE statements in revision 001. Rejected — makes the migration script non-standard, harder to maintain, and obscures the intent. `stamp` is the canonical Alembic pattern for this scenario.

---

### D4: Alembic config reads `DATABASE_URL` from environment

**Decision:** `alembic.ini` does not hardcode a database URL. Instead, `env.py` reads `DATABASE_URL` from the environment (same variable used by the backend app), overriding the `sqlalchemy.url` config option at runtime.

```python
# alembic/env.py (addition to run_migrations_online)
import os

def run_migrations_online() -> None:
    configuration = config.get_section(config.config_ini_section, {})
    # Override URL from environment — matches backend's DATABASE_URL pattern
    db_url = os.getenv("DATABASE_URL")
    if db_url:
        configuration["sqlalchemy.url"] = db_url

    connectable = engine_from_config(
        configuration,
        prefix="sqlalchemy.",
        poolclass=pool.NullPool,
    )
    # ...
```

**Alternative considered:** Set `sqlalchemy.url` in `alembic.ini` directly. Rejected — would require committing credentials or maintaining a separate secrets file. Environment variable is already the established pattern for this project.

## Data Storage

### `alembic_version` table

Alembic automatically creates and manages this table. It stores the current applied revision ID. No manual interaction required.

| Column | Type | Description |
|---|---|---|
| `version_num` | `VARCHAR(32)` | Current head revision ID |

## Interfaces

### CLI Commands (Alembic)

| Command | Description |
|---|---|
| `alembic upgrade head` | Apply all pending migrations |
| `alembic downgrade -1` | Roll back one revision |
| `alembic current` | Show currently applied revision |
| `alembic history` | Show full revision history |
| `alembic stamp head` | Mark current DB as being at head without running SQL (prod baselining) |
| `alembic revision --autogenerate -m "<msg>"` | Generate a new revision from model diff |

### Seed Script

```bash
# Run after alembic upgrade head for fresh environments
python seed_schedule.py
```

`seed_schedule.py` inserts the 2025 NFL schedule into the `schedule` table using `INSERT ... ON DUPLICATE KEY UPDATE` to be idempotent.

### `seed_schedule.py`

```python
#!/usr/bin/env python3
"""
Seed the 2025 NFL regular season schedule.
Run once per season after `alembic upgrade head`.
Idempotent — safe to re-run.
"""
import os
from sqlalchemy import create_engine, text
from dotenv import load_dotenv

load_dotenv()

SCHEDULE_DATA = [
    # (game_id, week_num, home_team_id, away_team_id, start_time)
    (401671834, 18, 33, 5, '2025-01-04 21:30:00'),
    # ... all rows from datamodel.sql schedule INSERT ...
]

def seed():
    engine = create_engine(os.environ["DATABASE_URL"])
    with engine.begin() as conn:
        for row in SCHEDULE_DATA:
            conn.execute(text("""
                INSERT INTO schedule (game_id, week_num, home_team_id, away_team_id, start_time, winning_team_id)
                VALUES (:game_id, :week_num, :home_team_id, :away_team_id, :start_time, 99)
                ON DUPLICATE KEY UPDATE week_num=VALUES(week_num)
            """), {
                "game_id": row[0],
                "week_num": row[1],
                "home_team_id": row[2],
                "away_team_id": row[3],
                "start_time": row[4],
            })
    print(f"Seeded {len(SCHEDULE_DATA)} schedule rows.")

if __name__ == "__main__":
    seed()
```

## Migrations

### Application order (fresh environment)

```text
1. alembic upgrade head      — creates all tables, inserts teams + rules
2. python seed_schedule.py   — inserts 2025 season schedule
3. uvicorn main:app          — start server
```

### Production baselining (one-time, first deploy only)

```text
1. Deploy code with Alembic added
2. alembic stamp head        — records current state without running DDL
3. alembic current           — verify: should show head revision
```

### Future revisions

```bash
# Author a new revision after changing models.py
alembic revision --autogenerate -m "add mfa secret column"

# Review the generated file in alembic/versions/, then apply
alembic upgrade head
```

### Rollback

```bash
alembic downgrade -1    # one step back
alembic downgrade base  # all the way back (destructive on prod — use with caution)
```

## Testing Philosophy

### Fresh environment setup

Run `alembic upgrade head` against a blank MySQL test database and verify all tables are created with the correct columns, types, constraints, and indexes. Verify team and rule seed data is present. Verify the command is idempotent (running twice does not error).

### Prod baselining path

Run `alembic stamp head` against a database that already has the schema applied manually (simulating prod). Verify the `alembic_version` table is created with the correct revision ID. Then verify `alembic upgrade head` is a no-op (no SQL executed, no errors).

### Seed script

Run `seed_schedule.py` against a seeded database and verify it completes without error (idempotency check via `ON DUPLICATE KEY UPDATE`). Verify row count matches expected schedule size.

### Downgrade

Run `alembic downgrade base` against the test database and verify all tables are dropped cleanly. Run `alembic upgrade head` again and verify full restoration.

## Risks / Trade-offs

### Prod baselining is a manual one-time step

**Risk:** If `alembic upgrade head` is accidentally run against production instead of `alembic stamp head` before baselining, it will attempt to re-create existing tables and fail loudly. No data loss risk — MySQL will error on duplicate table creation — but it could cause deployment anxiety or confusion.

**Mitigation:** Document the baselining procedure explicitly in deployment runbook. The `upgrade` failure is safe (no partial state) — it errors out before making changes. After stamping, subsequent `upgrade head` calls become a safe no-op.

### `datamodel.sql` divergence

**Risk:** `datamodel.sql` remains in the repo but is now stale and misleading. A developer unfamiliar with the project might treat it as authoritative.

**Mitigation:** Add a prominent comment at the top of `datamodel.sql` marking it as a historical reference, superseded by Alembic. Consider renaming it to `datamodel.sql.reference` or adding a `DEPRECATED.md` note alongside it in a follow-up.

### Autogenerate doesn't detect everything

**Risk:** Alembic autogenerate has known gaps: it does not detect changes to column server defaults, CHECK constraints, or certain index types on MySQL. If `models.py` and the live schema differ on these, the generated baseline may be incomplete.

**Mitigation:** After generating the baseline revision, review it manually and compare against `datamodel.sql` and the ad-hoc SQL files. The known schema changes (winning_team_id INT, uppercase enum) are both reflected in `models.py`, so the baseline should be accurate for current state.
